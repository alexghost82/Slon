## DEF-003 — `shell=True` in desktop action helpers
- Severity: MAJOR
- Priority: P1 / Before broader LAN exposure
- Confidence: High
- Reproducibility: static 1/1 (code paths present)
- Platforms/builds: source review; Linux brightness fallback; VS Code open helper
- Preconditions: tools `computer_settings` / `dev_agent` reachable under SafetyPolicy risk gates
- Steps to reproduce:
  1. `rg 'shell=True' actions/dev_agent.py actions/computer_settings.py`
  2. Observe `subprocess.Popen(..., shell=True)` when opening VS Code (`dev_agent._open_vscode`)
  3. Observe Linux brightness up/down fallback uses shell pipeline with `xrandr` (`computer_settings.py`)
- Expected: no shell invocation for tool helpers; argv lists only; policy tests already forbid `shell=True` in reminder/cmd paths
- Actual: **FIXED** — argv-only subprocess; Linux brightness uses `_linux_adjust_brightness_xrandr` (parse + argv); Windows `code.cmd` via `cmd.exe /c` list argv
- User/business impact: expands injection / unexpected shell parsing risk if malicious or malformed args reach those helpers; higher severity if LAN remote can trigger tools
- Evidence: `logs/sast-suites.txt` (original); post-fix: `fix-and-verify.md`; `rg` shows no `shell=True` under `actions/`
- Relevant logs: SAST-lite hits (historical)
- Suspected component/root cause: legacy convenience for Windows `code.cmd` path and Linux brightness without brightnessctl
- Workaround: avoid enabling LAN bind; keep high-risk tools behind confirm; prefer macOS paths (osascript without shell)
- Recommended fix: replace with argv-only subprocess; remove shell pipelines; add regression asserts in `tests/security`
- Verification test: `tests/security/test_beta_security_gates.py::test_no_subprocess_shell_true_in_dev_agent_or_computer_settings` — **PASS**
- Status: **fixed** (2026-08-15 fix-and-verify)
